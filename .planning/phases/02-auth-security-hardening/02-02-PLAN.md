Output: All 26 tables have RLS enabled with per-expert filtering policies.

**3. Create expert-scoped policies for all 26 tables:**
For each table, create 4 policies (SELECT, INSERT, UPDATE, DELETE). Use a DO block to loop:

```sql
DO $$
DECLARE
  tbl TEXT;
  tables TEXT[] := ARRAY[
    'leads', 'mensagens', 'followups_enviados', 'notificacoes', 'templates_mensagem',
    'configuracoes', 'mensagens_funil_v2', 'whatsapp_rotacao', 'whatsapp_rotacao_config',
    'whatsapp_rotacao_mensagens', 'whatsapp_eventos_log', 'moderacao_grupos',
    'moderacao_strikes', 'moderacao_log', 'agendamentos_mensagens', 'agendamentos_grupos',
    'torneios', 'participantes', 'greens', 'log_imagens', 'copys_geradas', 'expert_perfil',
    'blacklist_grupos', 'grupos_ignorar_coleta', 'telegram_canais', 'documents'
  ];
BEGIN
  FOREACH tbl IN ARRAY tables LOOP
    -- SELECT: expert sees only own rows
    EXECUTE format(
      'CREATE POLICY expert_select_%1$s ON %1$I FOR SELECT USING (expert_id::TEXT = current_setting(''app.expert_id'', true))',
      tbl
    );

    -- INSERT: expert can only insert with own expert_id
    EXECUTE format(
      'CREATE POLICY expert_insert_%1$s ON %1$I FOR INSERT WITH CHECK (expert_id::TEXT = current_setting(''app.expert_id'', true))',
      tbl
    );

    -- UPDATE: expert can only update own rows
    EXECUTE format(
      'CREATE POLICY expert_update_%1$s ON %1$I FOR UPDATE USING (expert_id::TEXT = current_setting(''app.expert_id'', true)) WITH CHECK (expert_id::TEXT = current_setting(''app.expert_id'', true))',
      tbl
    );

    -- DELETE: expert can only delete own rows
    EXECUTE format(
      'CREATE POLICY expert_delete_%1$s ON %1$I FOR DELETE USING (expert_id::TEXT = current_setting(''app.expert_id'', true))',
      tbl
    );
  END LOOP;
END $$;
```

**4. IMPORTANT — FORCE RLS for table owner too:**
By default, table owners bypass RLS. Since the anon role might not be the owner, but the RPCs run as SECURITY DEFINER (superuser), we need to ensure that:
- RPCs explicitly set app.expert_id before queries
- Direct anon queries without set_config return ZERO rows (because current_setting returns empty string which matches nothing)

Add FORCE ROW LEVEL SECURITY on tables to ensure even owner respects policies:
```sql
-- Force RLS even for table owner (prevents bypass)
DO $$
DECLARE
  tbl TEXT;
  tables TEXT[] := ARRAY[
    'leads', 'mensagens', 'followups_enviados', 'notificacoes', 'templates_mensagem',
    'configuracoes', 'mensagens_funil_v2', 'whatsapp_rotacao', 'whatsapp_rotacao_config',
    'whatsapp_rotacao_mensagens', 'whatsapp_eventos_log', 'moderacao_grupos',
    'moderacao_strikes', 'moderacao_log', 'agendamentos_mensagens', 'agendamentos_grupos',
    'torneios', 'participantes', 'greens', 'log_imagens', 'copys_geradas', 'expert_perfil',
    'blacklist_grupos', 'grupos_ignorar_coleta', 'telegram_canais', 'documents'
  ];
BEGIN
  FOREACH tbl IN ARRAY tables LOOP
    EXECUTE format('ALTER TABLE %I FORCE ROW LEVEL SECURITY', tbl);
  END LOOP;
END $$;
```

NOTE: The `service_role` key in Supabase ALWAYS bypasses RLS regardless of FORCE. This is how admin RPCs work (per D-03). The anon key respects RLS.

**5. Verify the existing app still works:**
After applying RLS, the existing frontend hooks use the anon key with direct `.from()` queries. Since they do NOT call `set_expert_context()`, `current_setting('app.expert_id', true)` will return empty string `''`, which means all direct queries will return ZERO rows.

This is EXPECTED and CORRECT behavior per D-02: "Migrate existing direct queries to RPCs gradually." During the transition:
- The app will temporarily show empty data until hooks are migrated to RPCs
- The admin_login RPC already calls set_expert_context, but that only persists for the RPC transaction

To prevent breaking the app during gradual migration, create a TEMPORARY fallback that will be removed when all hooks use RPCs. Add a "transition" policy that allows the anon role to SELECT when no expert context is set BUT only with a matching expert_id filter in the WHERE clause. ACTUALLY — DO NOT DO THIS. Per D-02, the plan is to migrate gradually. The correct approach is:

After RLS is applied, create a helper RPC that the frontend can call once after login to set the session expert context for subsequent direct queries:

```sql
-- Transition helper: frontend calls this after login to set context for the session
-- This allows existing .from() queries to work with RLS during migration
CREATE OR REPLACE FUNCTION set_session_expert(p_expert_id UUID)
RETURNS BOOLEAN AS $$
BEGIN
  -- Validate expert exists and is active
  IF NOT EXISTS (SELECT 1 FROM experts WHERE id = p_expert_id AND ativo = true) THEN
    RETURN false;
  END IF;

  PERFORM set_config('app.expert_id', p_expert_id::TEXT, false);
  -- false = persists for entire session (not just transaction)
  RETURN true;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

IMPORTANT: The `false` parameter in `set_config` makes it persist for the database session. However, Supabase uses connection pooling (PgBouncer in transaction mode), so each request gets a fresh connection. This means `set_config` with `false` still only works within a single Supabase client request.

REVISED APPROACH: Since Supabase connection pooling resets settings between requests, direct `.from()` queries CANNOT benefit from `set_config`. The only way for direct queries to work is:
1. Use Supabase Auth (we are NOT doing this per constraint)
2. Use RPCs that set context within the same transaction

Therefore: Keep the RLS policies as-is. They are correct. Direct queries will return empty. The migration to RPCs (D-02) will happen gradually in subsequent phases/plans. For THIS plan, just apply the RLS and verify it works correctly with the set_expert_context pattern.
