Output: All 26 tables have RLS enabled with per-expert filtering policies.

**3. Create expert-scoped policies for all 26 tables:**
For each table, create 4 policies (SELECT, INSERT, UPDATE, DELETE). Use a DO block to loop:

```sql
DO $$
DECLARE
  tbl TEXT;
  tables TEXT[] := ARRAY[
    'leads', 'mensagens', 'followups_enviados', 'notificacoes', 'templates_mensagem',
    'configuracoes', 'mensagens_funil_v2', 'whatsapp_rotacao', 'whatsapp_rotacao_config',
    'whatsapp_rotacao_mensagens', 'whatsapp_eventos_log', 'moderacao_grupos',
    'moderacao_strikes', 'moderacao_log', 'agendamentos_mensagens', 'agendamentos_grupos',
    'torneios', 'participantes', 'greens', 'log_imagens', 'copys_geradas', 'expert_perfil',
    'blacklist_grupos', 'grupos_ignorar_coleta', 'telegram_canais', 'documents'
  ];
BEGIN
  FOREACH tbl IN ARRAY tables LOOP
    -- SELECT: when app.expert_id is set (RPCs), filter by expert. When not set (direct queries), allow access (transition policy).
    -- As hooks migrate to RPCs in future phases, the IS NULL/empty fallback will be removed to enforce strict isolation.
    EXECUTE format(
      'CREATE POLICY expert_select_%1$s ON %1$I FOR SELECT USING (
        current_setting(''app.expert_id'', true) IS NULL
        OR current_setting(''app.expert_id'', true) = ''''
        OR expert_id::TEXT = current_setting(''app.expert_id'', true)
      )',
      tbl
    );

    -- INSERT: same transition logic
    EXECUTE format(
      'CREATE POLICY expert_insert_%1$s ON %1$I FOR INSERT WITH CHECK (
        current_setting(''app.expert_id'', true) IS NULL
        OR current_setting(''app.expert_id'', true) = ''''
        OR expert_id::TEXT = current_setting(''app.expert_id'', true)
      )',
      tbl
    );

    -- UPDATE: same transition logic for USING + WITH CHECK
    EXECUTE format(
      'CREATE POLICY expert_update_%1$s ON %1$I FOR UPDATE USING (
        current_setting(''app.expert_id'', true) IS NULL
        OR current_setting(''app.expert_id'', true) = ''''
        OR expert_id::TEXT = current_setting(''app.expert_id'', true)
      ) WITH CHECK (
        current_setting(''app.expert_id'', true) IS NULL
        OR current_setting(''app.expert_id'', true) = ''''
        OR expert_id::TEXT = current_setting(''app.expert_id'', true)
      )',
      tbl
    );

    -- DELETE: same transition logic
    EXECUTE format(
      'CREATE POLICY expert_delete_%1$s ON %1$I FOR DELETE USING (
        current_setting(''app.expert_id'', true) IS NULL
        OR current_setting(''app.expert_id'', true) = ''''
        OR expert_id::TEXT = current_setting(''app.expert_id'', true)
      )',
      tbl
    );
  END LOOP;
END $$;
```

**4. IMPORTANT — FORCE RLS for table owner too:**
By default, table owners bypass RLS. Since the anon role might not be the owner, but the RPCs run as SECURITY DEFINER (superuser), we need to ensure that:
- RPCs explicitly set app.expert_id before queries
- Direct anon queries without set_config return ZERO rows (because current_setting returns empty string which matches nothing)

Add FORCE ROW LEVEL SECURITY on tables to ensure even owner respects policies:
```sql
-- Force RLS even for table owner (prevents bypass)
DO $$
DECLARE
  tbl TEXT;
  tables TEXT[] := ARRAY[
    'leads', 'mensagens', 'followups_enviados', 'notificacoes', 'templates_mensagem',
    'configuracoes', 'mensagens_funil_v2', 'whatsapp_rotacao', 'whatsapp_rotacao_config',
    'whatsapp_rotacao_mensagens', 'whatsapp_eventos_log', 'moderacao_grupos',
    'moderacao_strikes', 'moderacao_log', 'agendamentos_mensagens', 'agendamentos_grupos',
    'torneios', 'participantes', 'greens', 'log_imagens', 'copys_geradas', 'expert_perfil',
    'blacklist_grupos', 'grupos_ignorar_coleta', 'telegram_canais', 'documents'
  ];
BEGIN
  FOREACH tbl IN ARRAY tables LOOP
    EXECUTE format('ALTER TABLE %I FORCE ROW LEVEL SECURITY', tbl);
  END LOOP;
END $$;
```

NOTE: The `service_role` key in Supabase ALWAYS bypasses RLS regardless of FORCE. This is how admin RPCs work (per D-03). The anon key respects RLS.

**5. Verify the existing app still works:**
After applying RLS, the existing frontend hooks use the anon key with direct `.from()` queries. Since they do NOT call `set_expert_context()`, `current_setting('app.expert_id', true)` returns empty string or NULL.

The transition policies above handle this correctly: when `app.expert_id` is NULL or empty, the policy allows access (permissive fallback). When `app.expert_id` IS set (via RPCs), it filters by expert_id. This means:
- Existing direct `.from()` queries continue working as before (transition mode)
- RPCs that call `set_expert_context()` get proper expert isolation
- As hooks are migrated to RPCs in future phases, the transition fallback (IS NULL/empty) will be removed to enforce strict isolation

Verify by running a direct query without set_config — should return ALL rows (transition mode). Then test with set_config to a specific expert_id — should return only that expert's rows.
